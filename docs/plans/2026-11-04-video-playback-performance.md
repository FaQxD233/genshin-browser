# 计划：视频播放卡顿排查与主窗渲染改造

> 状态：暂缓（2026-11-04）。WinUI 分支（没有截屏捕获链）同样卡；边玩原神边实测没有复现卡顿（第 7 节），待你下次遇到卡顿时记录条件再定。2.4 的 S1 / S2 已单独实施（2026-11-04，见 `2026-11-04-review-fixes.md`）
> 日期：2026-11-04
> 来源：用户 2026-11-04 反馈：播放视频时卡顿，页面缩放调到 70% 左右更卡
> 流程：本文件确认后再改代码

---

## 0. 结论

1. **卡顿的主因是主窗的渲染方式，不是网页本身。** 主窗用 `WebView2CompositionControl` 放在 `AllowsTransparency=True` 的分层窗里，网页的每一帧都要走一遍：系统截屏捕获（Windows.Graphics.Capture）→ 在 UI 线程拷进 D3DImage → WPF 重绘整个窗口 → 从显卡回读到内存 → `UpdateLayeredWindow` 交给 DWM。这条链按显示器刷新率跑（你的屏 165Hz，就是每秒 165 次），页面完全静止时也照跑。
2. **游戏占着显卡时，这条链跟不上。** 控件交帧时用 `TryLock(0)`，WPF 渲染线程还没忙完就把这一帧直接扔掉，于是画面间隔忽长忽短，看起来就是卡。同一时刻 Chromium 自己渲染完全正常（165 帧、视频 0 丢帧）。这条链还在和游戏抢显卡：模拟负载下，「游戏」帧率掉了约 27%。
3. **70% 缩放本身不影响这条链。** 缩小后同一个窗口里能放下更多内容（弹幕轨道更多、页面其它部分露出来），Chromium 的渲染量会上升，叠在本来就吃紧的显卡上。实测这部分影响很小、也不稳定（见 1.4、1.5），主因仍是第 1 条。
4. **建议**：主窗改用 HWND 版 `WebView2` + DWM 玻璃窗（逐像素透明）+ 分层窗整窗透明度（`LWA_ALPHA`）。这样画面由 DWM 直接合成，没有捕获和回读这一步。原型实测：同样负载下 0 丢帧，「游戏」帧率只掉约 5%；透明背景、不透明度、鼠标穿透这三项都已验证可行。
5. **修正（第 6 节）**：上面的测试里，模拟游戏的窗口不在浮窗下面，也没有全屏，所以没覆盖「半透明窗叠在无边框游戏上」时 DWM 的合成成本，也没有内存压力。WinUI 分支没有截屏捕获链，你实测同样卡，因此第 1、2 条只是 WPF 版独有的一项开销，不足以解释你的卡顿；第 4 条改造能去掉这项开销，但单独做未必能解决问题。

## 1. 实测

环境：RTX 5090 笔记本 GPU、i7-12650H、2560×1440 165Hz、缩放 125%；WebView2 运行时 156.0.4314.58，SDK 1.0.4078.44。

方法：临时测量程序（在 Claude 的 scratchpad 里，不进仓库）驱动真主窗（`MainWindow` + 浏览器内核），数据目录用 `GENSHINBROWSER_DATA_DIR` 指向 D 盘测试副本，窗口 658×370（你现在的尺寸），不透明度 80%。

- 测试页：ffmpeg 生成的 1080p30 H.264 视频铺满窗口，加模拟弹幕。轨道数按页面 CSS 高度算，所以缩放越小，轨道越多。
- 「游戏」负载：另开一个独立进程跑 WebGL 着色器，每帧 256 次绘制调用，约占 75% 的 3D 引擎。单独运行时约 30.5 帧。
- 指标：捕获到达帧数和交给 WPF 的帧数（反射读控件内部计数、订阅 D3DImage.Changed）；网页内 rAF、`requestVideoFrameCallback`、视频丢帧数；各进程 CPU 与 GPU 引擎占用。

测试前半段系统合成频率是 60Hz（当时可能在用虚拟显示器），那段数据只作参考。下面的数据都是在 165Hz 下测的。

### 1.1 现在的渲染链（反汇编 SDK 1.0.4078.44 确认）

- `InitializeCoreDispatcher` 在 UI 线程上建 DispatcherQueue，捕获帧池用 `Direct3D11CaptureFramePool.Create`，只有 1 个缓冲。所以每一帧的回调都在 WPF UI 线程上。
- 每帧依次执行：`TryGetNextFrame`，然后 `TryLock(0)`。拿不到锁就丢掉这一帧；拿到了就把整帧 `CopyResource`、整窗 `AddDirtyRect`，再 `Unlock`，WPF 随后重绘并重新提交整个分层窗。
- `FpsDivider`（降帧参数）在这个版本里是 internal，官方文档上的是预览版。

### 1.2 无负载

| 场景 | 捕获 / 交付（帧/秒） | 宿主进程 3D | 宿主 CPU | 备注 |
|---|---|---|---|---|
| 静态页面（无任何动画） | 164 / 164 | 10–12% | 约 4% | Chromium 的 GPU 进程和渲染进程都是 0%，页面不动也每秒整窗重绘 164 次 |
| 视频 + 弹幕，100% | 164.5 / 164.5 | 10% | 约 5% | |
| 视频 + 弹幕，70% | 164.2 / 164.2 | 13.7% | 约 5% | 弹幕节点 45 → 70 |
| 视频 + 弹幕，70%，窗口 1280×720 | 165 / 165 | 19.4%（DWM 3.8%） | 约 8% | 开销随窗口面积增长 |

这台显卡在没有负载时能扛住，所以不丢帧。但宿主进程平白占着约 10% 的 3D，显卡弱一些会更明显。

### 1.3 类游戏负载

| 场景 | 交付 / 捕获 | 丢帧 | 跳帧（帧间隔 > 中位数 1.8 倍） | 「游戏」帧率（单独约 30.5） |
|---|---|---|---|---|
| 现架构，静态页 | 155 / 165 | 6% | 约 7 次/秒 | 约 25 |
| 现架构，视频 + 弹幕 70% | 145 / 165 | 12% | 约 8 次/秒 | 21–24 |
| 同上，进程 GPU 优先级 HIGH | 145 / 165 | 12% | 无改善 | 无变化 |
| 同上，进程 GPU 优先级 REALTIME | 164 / 164 | 0% | 正常 | 16–19（游戏更卡） |
| 玻璃窗 + HWND 版 WebView2 | 无捕获链 | Chromium 0 丢帧 | rAF 165 帧，最大间隔 7ms | 约 28.5 |
| 同上 + 分层 / 穿透样式 | 无捕获链 | Chromium 0 丢帧 | rAF 165 帧，最大间隔 7ms | 约 28.8 |

另外测了一种「每帧一次超大绘制、显卡无法中途抢占」的负载，算是最坏情况：现架构丢帧 69–70%，实际只剩约 48 帧/秒，帧间隔在 19–33ms 之间跳。这时 Chromium 依然 165 帧、视频 0 丢帧。

### 1.4 缩放与内存目标（类游戏负载下交替各测 3 轮）

- 100% 对 70%：丢帧率全是 12%，跳帧次数 107/92/84 对 97/98/82，看不出差别。
- 内存目标 Normal 对 Low：丢帧率相同（12%），跳帧 85/92/78 对 104/104/99。Low 三轮都多约 20%，影响轻微但方向一致。

### 1.5 真实 B 站页面（测试副本，未登录，360p）

- 100% 对 70%：渲染进程 CPU 2.0% 对 3.3%，GPU 进程 3D 0.3% 对 0.7%，弹幕节点 23 对 31，捕获链完全相同。
- 视频暂停后的一段（165Hz）里，70% 的 rAF 跳帧 21 次、最长 109ms；100% 是 9 次、最长 73ms。
- 结论：70% 下 Chromium 工作量确实更大，但量级小。登录后的高码率视频、你实际的弹幕密度和游戏负载可能放大这一点，这边没法复现。

### 1.6 试过、不采用的办法

| 办法 | 结果 |
|---|---|
| `FpsDivider = 2`（反射设置） | 交付 22 帧/秒，间隔 32/64ms 交替，更不均匀 |
| 进程 GPU 调度优先级 HIGH / REALTIME | HIGH 无效；REALTIME 不丢帧，但「游戏」从约 30 帧掉到 16–19 帧 |
| WPF 软件渲染 | D3DImage 不出画面（交付 0） |
| Composition 控件放进普通（非分层）窗口 | 只剩约 10 帧/秒（TryLock 抢不到锁） |

### 1.7 透明方案验证（屏幕角落放一块青色背景窗，取像素）

| 验证项 | 取到的颜色 | 结论 |
|---|---|---|
| 玻璃窗（`GlassFrameThickness=-1`、背景透明），WPF 半透明蓝 `#800000FF` | (0,127,255) | 恰好是 50% 混合 |
| HWND 版 WebView2，透明底，页面背景透明 | (0,255,255) | 透出背后的青色，逐像素透明成立 |
| 窗口钩子抢先处理 `WM_STYLECHANGING` 后加上 `WS_EX_LAYERED`，`LWA_ALPHA=128` | WPF 部分 (0,191,255)，不透明网页 (128,127,255) | 整窗透明度对 WPF 和网页同时生效，并能和逐像素透明叠加 |
| 再加 `WS_EX_TRANSPARENT` | `WindowFromPoint` 返回背后的窗口 | 鼠标穿透成立，内嵌 WebView 区域也穿透 |
| 不加钩子 | 写入的分层样式被 WPF 改回去 | WPF 的 HwndSource 会剥掉非 `AllowsTransparency` 窗口的分层位，必须用钩子 |
| CSS 方案：页面背景透明，内容放在全屏元素里，`html{opacity:.5}` | (127,128,255) | 也可行（备选） |

## 2. 方案

### 2.1 主窗渲染（R1）

- `MainWindow.xaml`：`AllowsTransparency="False"`；`WindowChrome` 的 `GlassFrameThickness` 由 0 改为 -1；窗口和根 Grid 背景改透明；`wv2:WebView2CompositionControl` 换成 `wv2:WebView2`，去掉 `ForceCursor`。
- `SourceInitialized`：
  - `HwndTarget.BackgroundColor = Transparent`；
  - 加 `WM_STYLECHANGING` 钩子：只处理 `GWL_EXSTYLE`，强制保留 `WS_EX_LAYERED`，`WS_EX_TRANSPARENT` 跟随鼠标穿透状态，然后标记已处理，跳过 WPF 剥分层位的那段逻辑；
  - 加上分层样式，用 `SetLayeredWindowAttributes` 设整窗透明度。
- Windows 11 圆角与边框：用 `DwmSetWindowAttribute` 关掉（不圆角、无边框色），保持现在的直角无边外观（实施时目测核对）。
- `ApplyWindowOpacity`：从设控件的 `Opacity` 改为设整窗 `LWA_ALPHA`（见第 5 节第 2 问）。
- `WindowModeService.SetClickThrough`：仍然翻转 `WS_EX_TRANSPARENT`，期望状态交给上面的钩子统一维护；注释里「AllowsTransparency 分层窗」的说法同步改掉。
- 页面注入脚本不变：`html,body` 透明背景照旧，玻璃窗下空白处照样透出游戏。

### 2.2 原来叠在网页上的 WPF 元素（R2）

HWND 版 WebView2 之上不能再画 WPF 内容（airspace），有三处要改：

| 元素 | 现在 | 改为 |
|---|---|---|
| 底部 OSD 提示 `MainToastBorder` | 主窗里的 Border | 独立的透明 `Popup`（不抢焦点、不挡鼠标），跟随主窗底部居中；动画与文案逻辑不变 |
| 模式切换描边闪 `ModeFlashBorder` | 主窗里的 Border | 与主窗同尺寸的透明 `Popup`，只画 2px 描边，闪完关闭 |
| 浮窗顶部感应条 `TitleBarHitZone` | 透明 Border 收 MouseEnter | 复用现有鼠标离开检测的定时器：浮窗、标题栏隐藏且未开穿透时，每 100ms 查一次光标是否进了顶部 30px |

### 2.3 连带改动

- 删掉光标守护（`AttachCursorGuard` / `DetachCursorGuard` 及字段）：HWND 版由浏览器自己管理光标。页面里 `video{cursor:default}` 的 CSS 保留。
- `CreateBrowserControl`、`RecreateBrowserAsync`、事件挂接等方法签名里的控件类型改为 `WebView2`。
- 键盘：按文档，HWND 版会把加速键（Ctrl 组合键、Esc 等不产生字符的键）作为 WPF 键盘事件抛出，`Ctrl+=/-/0` 和视频铺满时的 Esc 预计照常工作。实施时逐项验证，不行就改走 `AcceleratorKeyPressed`。
- 鼠标离开时向页面补发 CDP 事件的逻辑保留（B 站控制栏仍需要）。
- 附带好处：Composition 控件不支持 DRM 内容，HWND 版支持（B 站部分付费 / 番剧内容）。
- TFM 保持 `net8.0-windows10.0.19041.0` 不动；改完后更新相关记忆（透明度不再依赖 Composition 控件）。

### 2.4 可选小项

S1、S2 已于 2026-11-04 实施（与第 2 节大改造无关），实施与实测见 `2026-11-04-review-fixes.md`。

| 编号 | 项 | 依据 | 改动量 |
|---|---|---|---|
| S1 | 内存目标只在窗口最小化 / F7 隐藏时设 Low，可见时一律 Normal | 官方文档说 Low 用于不活动或隐藏的 WebView，可能把内存换出到磁盘；实测 Low 跳帧多约 20%（现架构下）。代价是边玩边看时多占一些内存 | 约 5 行 |
| S2 | 控制窗地址栏加载条（无限循环动画）只在加载时运行 | 第一次导航后动画永远不停，控制窗隐藏时也在每帧驱动 WPF 渲染；实测开销很小，属于顺手清理 | 2 个 XAML |

### 2.5 不采用

第 1.6 节那四种办法，外加「保留 Composition 控件、只换窗口类型」（会掉到约 10 帧/秒）。

## 3. 行为变化

- 不透明度如果选整窗 `LWA_ALPHA`（推荐）：标题栏和窗口边缘也会跟着变透明。浮窗模式下标题栏平时是隐藏的，主要影响浏览模式的观感。OSD 和描边是独立的小窗，不受影响。
- 网页全屏（视频铺满）、页面弹层这类「顶层」元素：整窗透明度天然覆盖。如果选 CSS 方案，这些要单独加规则。
- 透明（玻璃）区域的鼠标命中：按窗口矩形判定，与现在近透明背景 `#01000000` 的效果一致，空白处不会误穿透。
- 半透明叠在无边框游戏上时，DWM 每帧都要合成，这部分开销无法避免（WinUI 分支 7 月的记录也是这个结论）。这次去掉的是在这之上、多出来的捕获和回读那条链。

## 6. 补充：WinUI 分支也卡（2026-11-04）

### 6.1 两个分支的异同（查代码确认）

| | 主线（WPF） | WinUI3-Experimental |
|---|---|---|
| WebView2 托管 | `WebView2CompositionControl`（截屏捕获 → D3DImage） | WinUI 自带 `WebView2`（合成方式托管，没有捕获） |
| 透明 | `AllowsTransparency` 逐像素分层窗 + 控件 `Opacity` | `WS_EX_LAYERED` + `LWA_ALPHA` 整窗 |
| 页面背景 | 注入 CSS 改透明 | 不透明（`#FF101010`），没有透明页面 CSS |
| 内存目标 | 浮窗 / 失焦时设 `Low` | 已删除，不设置 |
| 共同点 | 半透明置顶窗叠在游戏上；Edge 内核与游戏争 GPU / CPU；同一台机器和显示环境 | 同左 |

### 6.2 主线独有：浮窗时 `Low` 会周期性修剪工作集

测试副本、浮窗模式、视频 + 弹幕，每秒采样一次：

| | GPU 进程工作集 | 浏览器进程 | 渲染进程 | 缺页 |
|---|---|---|---|---|
| Normal | 100–114MB | 约 115MB | 94–115MB | 渲染进程每秒几十到一千多次 |
| 切到 Low 的那一秒 | 20MB | 1MB | 39MB | GPU 进程约 5300 次、渲染进程约 10000 次 |
| Low 期间 | 每 10 多秒再剪一次（如 40→28MB） | 约 10MB | 缓慢回升 | 每次修剪伴随几千次缺页 |

没有内存压力时，这对网页流畅度没有可测影响：rAF 和视频帧间隔与 Normal 一样，进程优先级、内存优先级、EcoQoS 也都没变。原神占用大量内存时，被剪掉的页面可能已被挪作他用，就得从页面文件读回。WinUI 分支没有这条策略却同样卡，所以它不是两边共有的原因，但 2.4 的 S1 仍然值得做。

### 6.3 还没排除的共同原因

1. **DWM 合成**：半透明置顶窗盖在无边框全屏游戏上时，游戏失去独立翻转，DWM 每帧都要合成整屏并混合浮窗。WinUI 分支 7 月记录过「DWM CPU 极高」。我这次的测试没有覆盖这种情况。
2. **Edge 内核被游戏抢占**：模拟负载下 Chromium 没有掉帧；原神的 GPU / CPU 负载更重，Chromium 自己会不会掉帧，还不知道。
3. **显示环境**：测试开头那段系统合成频率是 60Hz（这台机器装有 GameViewer 虚拟显示器，当时可能在被远程连接），网页只跑 56.8 帧，30 帧视频每秒丢约 1.6 帧。HWND 版 WebView2 同样如此，与程序无关。如果平时是串流 / 远程玩，这一条会一直存在。

### 6.4 下一步：在真实场景测

- 方案 A（推荐）：你玩原神时运行测量程序，同一个视频依次用三种窗口各放 40 秒：现主线、类 WinUI（整窗 LWA）、玻璃窗 + HWND 版 WebView2。程序记录 Chromium 的帧间隔与丢帧、捕获链交付、各进程 CPU / GPU、DWM 占用，你同时记下哪段卡。这样能看出帧丢在哪一层。想用平时的清晰度，需要在真程序关闭时把登录状态复制到测试副本。
- 方案 B：我在这边用全屏无边框的 GPU 负载窗口模拟游戏，浮窗盖在上面测。这会占满屏幕约 2 分钟。
